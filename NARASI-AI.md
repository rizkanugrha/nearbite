# 6.1 Narasi Pemanfaatan AI

## Pendahuluan

Dalam pengembangan NearBite, AI saya gunakan sebagai asisten berpikir, bukan sebagai pengganti pemahaman atau pengujian. NearBite adalah aplikasi Flutter untuk mencari restoran terdekat, menampilkan menu, serta menyediakan autentikasi dan CRUD bagi pemilik restoran. Karena proyek ini berkembang lintas beberapa paket dan perangkat, strategi saya terhadap AI juga berubah. Pada sesi-sesi awal, bantuan AI terutama digunakan untuk memahami syntax Dart, widget Flutter, dan pola dasar `ChangeNotifier`. Setelah struktur aplikasi mulai terbentuk, pertanyaan saya bergeser ke data layer, kontrak API, pemetaan JSON, autentikasi, GPS, upload foto, testing, dan release Android. Pada tahap akhir, AI lebih banyak saya gunakan untuk audit risiko, membaca diagnostic, dan membantu menyusun dokumentasi.

## Evolusi Strategi AI

Pada tahap awal, saya memanfaatkan AI untuk hal-hal kecil yang terlihat langsung di layar: arti `final`, `const`, `notifyListeners()`, `WidgetsFlutterBinding.ensureInitialized()`, struktur `StatefulWidget`, dan cara memakai `Consumer`. Fokusnya adalah syntax dan widget. Saya belajar bahwa perubahan state tidak otomatis terlihat UI; provider harus mengubah state lalu memanggil `notifyListeners()`. Saya juga memahami bahwa `const` membuat object widget yang nilainya tetap dapat digunakan kembali Flutter, sehingga pekerjaan rebuild dapat dikurangi. Pada tahap ini AI berfungsi seperti tutor dan pemberi contoh, tetapi saya tetap membaca ulang kode untuk memastikan contoh tersebut cocok dengan versi Flutter yang digunakan.

Tahap berikutnya masuk ke data layer. Domain NearBite bukan lagi contoh counter sederhana, tetapi memiliki `User`, `Restaurant`, dan `MenuItem`, relasi owner-restoran-menu, serta response JSON Supabase. Ketika domain baru dimodelkan, saya tidak cukup hanya meminta AI membuat class. Saya harus menentukan field wajib, nullable, nama kolom database, konversi `fromJson`, `toJson`, dan perilaku `copyWith`. Contohnya, `User` berada di domain dan tidak boleh bergantung pada `SharedPreferences`; penyimpanan session diletakkan pada `AuthLocalStorage` di data layer. Perubahan domain seperti ini membuat saya lebih memperhatikan batas tanggung jawab: model mendeskripsikan data, API client mengurus HTTP, provider mengurus state, dan screen mengurus interaksi pengguna.

Pada tahap Proyek Akhir, strategi AI menjadi lebih berbasis risiko. Saya meminta bantuan untuk meninjau alur autentikasi Supabase, token cached, permission GPS, upload foto melalui `image_picker`, koneksi internet, sealed error, dan race condition setelah `await`. AI membantu menemukan bahwa data owner perlu dibersihkan saat logout, callback GPS harus memeriksa `mounted`, dan Bluetooth tidak boleh dianggap sebagai bukti adanya internet. Untuk release, saya menggunakan AI untuk membaca error activity Android, memeriksa konfigurasi `applicationId`, membersihkan build lama, serta membandingkan hasil debug dan release APK. Namun setiap saran tetap diverifikasi dengan source, analyzer, test, dan perangkat/emulator.

## Keputusan Menerima dan Menolak Saran AI

Kasus pertama adalah pengelolaan API key. Saran awal yang mungkin diberikan AI adalah menaruh URL dan anon key langsung sebagai konstanta di `main.dart` agar aplikasi mudah dijalankan. Saya menerima pola konfigurasi `String.fromEnvironment`, tetapi menolak hard-code key asli di dokumentasi dan source. Keputusan teknisnya adalah nilai konfigurasi diberikan melalui `--dart-define`, sedangkan README hanya berisi placeholder. Ini mengurangi risiko kebocoran credential dan membuat konfigurasi development/release dapat dibedakan. Anon key bukan password server, tetapi tetap tidak seharusnya disebarkan sembarangan, terutama jika konfigurasi RLS belum benar.

Kasus kedua adalah lokasi. AI dapat menyarankan menghitung jarak langsung di dalam `build()` agar daftar selalu terlihat terbaru. Saran itu saya tolak. Perhitungan jarak dipindahkan ke fungsi pure Dart `calculateDistance()` dan provider hanya menggunakannya saat lokasi atau data restoran berubah. Alasannya, `build()` seharusnya fokus membangun UI, bukan melakukan kalkulasi domain berulang pada setiap rebuild. Pemisahan ini juga membuat formula Haversine dapat diuji tanpa widget, permission, emulator, atau koneksi internet.

Kasus ketiga adalah password dan session. Saya menolak saran menyimpan password plain di `SharedPreferences`. Yang disimpan hanya token dan metadata minimum user melalui `AuthLocalStorage`; password dikirim ke Supabase Auth saat login/register dan tidak disimpan lokal. Saya juga menerima perbaikan untuk memvalidasi token cached melalui endpoint `/auth/v1/user`, tetapi dengan batasan: jika validasi gagal karena `NetworkError`, session lokal tidak langsung dihapus agar aplikasi tidak mengeluarkan user hanya karena sedang offline. Jika server mengembalikan `401`, session dibersihkan karena token memang tidak lagi valid.

Kasus keempat adalah testing API. Saya menolak test yang memanggil server Supabase sungguhan. Test seperti itu lambat, bergantung jaringan, dapat mengubah data, dan tidak deterministik. Sebagai gantinya, `http.Client` diberi mock/fake response sehingga status `200`, `401`, `404`, `422`, dan `500` dapat diuji berulang. Untuk device feature, `MockLocationService` dan `MockConnectivity` digunakan agar test tidak bergantung pada GPS atau radio emulator.

## Verifikasi Pemahaman

Pemahaman saya diverifikasi dengan tiga cara. Pertama, saya menjalankan `flutter analyze` untuk menemukan masalah tipe, import, lifecycle, dan lint. Hasil terakhir tidak memiliki error compile, tetapi masih ada 17 info/warning ringan yang dijelaskan di README, misalnya saran `const`, dua `avoid_print`, dan satu unused import pada test. Tidak ada `// ignore:` yang digunakan untuk memaksa hasil hijau.

Kedua, saya menjalankan `flutter test` dan mendapatkan 85 test lulus. Contoh unit testnya adalah mapping `ApiError`, parsing model, kalkulasi jarak, behavior filter radius, sorting harga, dan transisi online/offline. Test widget berjumlah lima pada `widget_test.dart`, mencakup nama menu kosong, harga non-numerik, harga negatif, data valid, dan batas harga sembilan digit. Jadi pengujian tidak hanya berupa unit test; setidaknya lima skenario widget juga dijalankan.

Ketiga, saya melakukan uji fungsional pada APK release. Saya memeriksa aplikasi dapat dibuild menjadi `app-release.apk` dengan ukuran sekitar 21 MB, memasang debug APK pada emulator, membuka activity launcher, menguji daftar restoran, login, CRUD menu, dan alur offline. Untuk GPS, saya menguji kondisi permission ditolak atau layanan lokasi tidak tersedia. Hasilnya aplikasi tidak crash; `LocationDenied` atau `LocationUnavailable` dikirim sebagai nilai dan UI menampilkan pesan lalu tetap dapat menampilkan daftar tanpa sorting jarak.

## Penjelasan Teknis End-to-End

Satu jalur end-to-end dimulai ketika pengguna membuka `RestaurantListScreen`. Screen meminta lokasi melalui `LocationService`, kemudian memanggil `RestaurantProvider.setUserLocation()`. Provider mengubah state dan memanggil `notifyListeners()`. Saat data restoran dimuat, provider memanggil `RestaurantApiClient.getRestaurants()`. API client adalah batas repository pada implementasi ini dan menggunakan datasource HTTP `http.Client` menuju Supabase PostgREST. Response JSON dipetakan menjadi `Restaurant`, provider mengurutkan dengan fungsi Haversine, lalu `Consumer<RestaurantProvider>` membangun ulang daftar UI. Jadi alurnya adalah UI → Provider → API client sebagai repository boundary → HTTP/Supabase datasource → model domain → Provider → UI.

`sealed ApiError` dipakai karena jenis kegagalan penting bagi keputusan UI. Status `401` berarti autentikasi tidak sah, sehingga berbeda dari `404` yang berarti resource tidak ditemukan dan `500` yang berarti masalah server. `401` pada validasi session menyebabkan token lokal dibersihkan dan user kembali unauthenticated. `404` dapat ditampilkan sebagai data tidak ditemukan, sedangkan `500` sebaiknya memberi opsi coba lagi. Dengan sealed class, kode dapat menangani kategori error yang eksplisit, bukan membandingkan string exception yang rapuh.

`LocationResult` juga sealed, dengan `LocationSuccess`, `LocationDenied`, `LocationUnavailable`, dan `LocationError`. Permission ditolak bukan selalu programming exception; itu keputusan pengguna atau kondisi perangkat yang masih dapat ditangani secara normal. Karena itu hasilnya dikembalikan sebagai nilai. UI dapat menampilkan pesan yang sesuai tanpa membuat aplikasi crash. Pendekatan ini juga memudahkan mock dan test.

Fungsi jarak dipisahkan dari UI karena Haversine adalah aturan domain yang deterministik. Ia menerima koordinat dan mengembalikan kilometer, tanpa `BuildContext`, widget, API, atau GPS. Dengan demikian test dapat memeriksa titik yang sama, simetri jarak, dan jarak Jakarta-Bogor secara cepat dan konsisten.

## Refleksi Kejujuran Akademik

Analisis domain, keputusan pemisahan `User` dari `AuthLocalStorage`, pemilihan GPS sebagai fitur utama, interpretasi kebutuhan owner, dan penilaian risiko backend merupakan pemahaman saya. Saya juga bertanggung jawab menjalankan aplikasi, memeriksa hasil test, mencoba permission ditolak, dan menentukan apakah saran AI dapat diterima.

AI membantu menjelaskan syntax, memberi alternatif struktur, menemukan potensi lifecycle bug, membuat contoh mock test, membaca output tool, dan menyusun dokumentasi awal. AI tidak saya anggap sebagai sumber kebenaran otomatis. Saran yang menyentuh keamanan, arsitektur, atau test saya cek terhadap source dan hasil eksekusi. Narasi ini ditulis ulang dengan kata-kata sendiri supaya saya dapat menjelaskan saat live demo, terutama alasan `notifyListeners`, perbedaan `401/404/500`, sealed result device, serta alasan fungsi jarak tidak ditempatkan di `build()`. Jika suatu bagian tidak dapat saya jelaskan kembali tanpa membuka jawaban AI, bagian itu belum saya anggap selesai dipahami.
